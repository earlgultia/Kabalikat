# Architecture

The client is a Vite + React + TypeScript single-page application. React Router handles navigation, TanStack Query is available for server state, and the Supabase browser client uses only public URL/key environment variables. Auth state comes from Supabase Auth; tenant memberships and role data come from PostgreSQL.

Disaster advisories use a separate Captain/Secretary publishing workflow. Drafts are visible only to managers; published advisories are readable to authorized members of that barangay. Publishing and resolution changes are audited. The interface makes clear that advisories do not contact emergency services.

The Phase 6 support portal scopes requester access to their own active-tenant tickets. Platform administrators have a separate support queue and can write internal-only notes; requesters can read only public replies. Ticket status changes are recorded in an append-only event log.

Subscription plan metadata and admin-managed trial/status records are visible only to platform administrators. New barangays receive a Free record. Payment processing is not connected, and plan entitlements are not used to gate access until a billing and continuity policy is configured.

PostgreSQL is the source of truth for identity, tenant membership, roles, permissions, resident and household records, document workflows, announcements, meetings, attendance, and archive metadata. Each feature has an isolated page and typed data-access module in `src/features/operations/`. Row Level Security protects reads and direct writes; security-definer RPCs handle invitation and archive flows, resident registration, document transitions, meeting creation, and attendance. Supabase Storage holds archive files in a private tenant-scoped bucket.

The app includes a separate platform administration shell and barangay workspace. The platform workspace can onboard a barangay and create its first Captain invitation. Its directory returns only tenant metadata and aggregate active membership counts. Workspace overview counts are computed in a tenant-scoped database function and returned only for permissions the active user holds. Committee workspaces use explicit member assignment, database-enforced reads, action-item ownership, and append-only activity records. The SK project workspace uses separate SK management and Captain review permissions and stores project progress apart from the finance ledger. Resident incident reports are visible only to their submitter and authorized barangay Captains. Tanod reports are visible to their submitter, authorized Captains, and the active Tanod assigned to respond. Captains assign only active Tanods in the same barangay; assigned responders can acknowledge and add updates, while Captains control resolution and closure. Mutations and response notes are recorded in an append-only event table. Patrol scheduling is Captain-managed and Tanod-assigned; shift logs are manually entered, append-only, and visible only to the barangay Captain or assigned Tanod. The patrol workspace does not use live location tracking. Phase 2 workflows and Phase 3 archive and meeting features rely on database permissions for enforcement. QR check-in uses short-lived hashed attendance tokens and authenticated attendee validation. Meeting reports use browser print-to-PDF. Phase 4 includes tenant-scoped annual budgets with approved amendments, transactions and linked adjustments with Treasurer submission and Captain approval, server-enforced expense ceilings, audited voiding, private receipt attachments, and logged date-range CSV exports gated by finance permissions. OCR processing, subscriptions, billing, email/SMS, and other specialized workspaces are not implemented.
