# Architecture

The client is a Vite + React + TypeScript single-page application. React Router handles navigation, TanStack Query is available for server state, and the Supabase browser client uses only public URL/key environment variables. Auth state comes from Supabase Auth; tenant memberships and role data come from PostgreSQL.

The account security dialog lets a signed-in user update their password through Supabase Auth. The sign-in page can request a reset email that returns to the `/reset-password` route. Password changes do not write values into the KABALIKAT database; the auth provider keeps the active workspace mounted when Supabase emits the user-updated event. Email delivery and allowed redirect URLs must be configured in Supabase Auth.

Workspace tool search filters the current role's allowed module navigation only; it does not search private resident or operational records. Ctrl/Cmd+K opens the keyboard-accessible finder, and the support shortcut navigates to the existing support module.

Users with multiple active barangay memberships can select among the memberships loaded from their authenticated profile. The selection is only a navigation preference; every data query and RPC remains tenant-scoped and rechecks the active membership and permissions in PostgreSQL.

The auth provider refreshes membership and platform-admin state when the page regains focus, with a 30-second throttle. It removes cached queries for tenant memberships no longer returned to the user and when switching away from a tenant.

The workspace update panel fetches published announcements and disaster advisories through their existing tenant RLS policies. It shows titles and dates only, excludes expired or draft items, and links to the authorized feature pages; it is an in-app current-updates view, not a push or email notification service.

Disaster advisories use a separate Captain/Secretary publishing workflow. Drafts are visible only to managers; published advisories are readable to authorized members of that barangay. Publishing and resolution changes are audited. The interface makes clear that advisories do not contact emergency services.

The general project workspace allows all active tenant members to read project status and reserves project creation, controlled status changes, progress updates, and milestone updates to Captains, Secretaries, and Kagawads. Project data uses tenant-scoped RLS and does not replace the finance ledger. The Phase 6 support portal scopes requester access to their own active-tenant tickets. Platform administrators have a separate support queue and can write internal-only notes; requesters can read only public replies. Ticket status changes are recorded in an append-only event log.

Subscription plan metadata and admin-managed trial/status records are visible only to platform administrators. New barangays receive a Free record. Payment processing is not connected, and plan entitlements are not used to gate access until a billing and continuity policy is configured.

PostgreSQL is the source of truth for identity, tenant membership, roles, permissions, resident and household records, document workflows, announcements, meetings, attendance, archive metadata, and outreach schedules. Each feature has an isolated page and typed data-access module in `src/features/operations/`. Row Level Security protects reads and direct writes; security-definer RPCs handle invitation and archive flows, resident registration, document transitions, meeting creation, attendance, and outreach scheduling/review.

The app includes a public landing page, a separate platform administration shell, and a barangay workspace with general project tracking. The platform workspace can onboard a barangay and create its first Captain invitation. Its directory returns only tenant metadata and aggregate active membership counts. Workspace overview counts are computed in a tenant-scoped database function and returned only for permissions the active user holds. Committee workspaces use explicit member assignment, database-enforced reads, action-item ownership, and append-only activity records. The SK project workspace uses separate SK management and Captain review permissions and stores project progress apart from the finance ledger. Resident incident reports are visible only to their submitter and authorized barangay Captains. Tanod reports are visible to their submitter, authorized Captains, and the active Tanod assigned to respond. Captains assign only active Tanods in the same barangay; assigned responders can acknowledge and add updates, while Captains control resolution and closure. Mutations and response notes are recorded in an append-only event table. Patrol scheduling is Captain-managed and Tanod-assigned; shift logs are manually entered, append-only, and visible only to the barangay Captain or assigned Tanod. The patrol workspace does not use live location tracking. Phase 2 workflows and Phase 3 archive and meeting features rely on database permissions for enforcement. QR check-in uses short-lived hashed attendance tokens and authenticated attendee validation. Meeting reports use browser print-to-PDF. Phase 4 includes tenant-scoped annual budgets with approved amendments, transactions and linked adjustments with Treasurer submission and Captain approval, server-enforced expense ceilings, audited voiding, private receipt attachments, and logged date-range CSV exports gated by finance permissions. OCR providers, billing, email/SMS delivery, health workflows and youth registries remain unimplemented.

Inter-barangay referrals use permission-checked RPCs, disclose only the referral payload to the origin and receiving officials, record access and workflow events, and never provide access to another barangay's resident registry.

Incident evidence files use short-lived upload intents and a private Storage bucket. RLS limits attachment metadata and downloads to the incident Captain or currently assigned Tanod, and successful uploads appear in incident history.

Captains can add a verified external handoff event to an active incident. The RPC requires a recipient, handoff details, and explicit confirmation, then appends to the incident history. It does not make calls or contact external responders.

Health outreach is an event-scheduling workflow: BHWs submit schedules, Captains independently review them, and published events are visible to active barangay members. It does not keep patient or participant records and is not a clinical system. SK event scheduling follows the same public schedule boundary: SK Chairpersons submit events for Captain review; the feature does not register youth, track attendance, or keep participant records. OCR providers, billing, email/SMS delivery, clinical health workflows and youth registries remain unimplemented.
