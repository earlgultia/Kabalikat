# Security notes

- Foundation and Phase 2 tables enable RLS; authenticated grants are limited to the operations required by their policies. Public and anonymous access is revoked.
- Tenant access is resolved from active database memberships and role permission mappings, never browser-supplied roles.
- The workspace selector lists only active barangay memberships returned for the signed-in user. Its saved selection is a local UI preference, not an authorization claim; all reads and writes remain protected by tenant-scoped RLS and permission checks.
- Active memberships are refreshed when the app returns to the foreground (throttled to once per 30 seconds). Tenant query cache is removed when membership access disappears or the user switches workspaces; database RLS and permission checks remain authoritative.
- Signed-in users can change their own password through Supabase Auth. Password values are validated in the client, sent directly to Auth over the configured Supabase client, and are not stored in application tables or audit logs.
- Password recovery uses Supabase Auth email and the `/reset-password` redirect route. The sign-in page returns a generic confirmation to avoid revealing whether an account exists. The Supabase Auth email provider and deployed redirect URL must be configured for this flow to work.
- Platform administrator identity remains separate from tenant membership and does not grant resident or operational record access.
- Critical writes use security-definer RPCs with an empty search path, explicit tenant checks, and authenticated execute grants. Invitation tokens are stored only as hashes and acceptance checks the signed-in email.
- Document, meeting, attendance, and announcement changes have database event records. Event tables have read policies and no client write grants.
- Issued-document revocation is limited to users with the tenant's `document.issue` permission, requires a reason, and writes an audit event. Residents can see the revocation status and reason for their own issuance; no client-side table write is granted.
- Document-request activity is returned through a tenant-scoped RPC to users with `document.request.read` or residents who own requests in that barangay. It returns display names rather than actor account IDs; request data remains subject to its existing resident/staff access rules.
- The UI hiding a module is not authorization; every feature operation is independently protected by RLS or database permission checks.
- Invitation links are bearer tokens until consumed or expired. Deliver them only through an approved private channel; the app does not send them.
- Account creation is offered only on the invitation route. Creating a Supabase Auth user does not create a tenant membership; the invitation RPC checks the hashed token, expiry, pending status, and authenticated email before it inserts membership.
- Captains can revoke pending invitations. The database rejects expired or already-used links, and invitation creation, acceptance, and revocation are stored in a protected event table.
- Archive files use a private Storage bucket, one-minute signed links, and tenant-scoped read policies. Upload objects require a short-lived, user-bound database intent, and archive metadata is registered only after Storage confirms the object and file metadata.
- Inter-barangay referrals use a separate server-checked disclosure workflow. Destination lookup returns only active barangay metadata; referral records have no direct client table grants and are returned through an RPC that records each authorized access. Referral creation requires an explicit policy/basis statement and confirmation, and an optional incident reference must belong to the origin barangay and be managed by the caller. The workflow does not verify legal authority; deployments must define and review their disclosure policy before use.
- Referral activity is returned through a security-definer RPC that checks origin create or receiving review permission for each record. It exposes only the action, actor display name, and timestamp for referrals visible to that official; the event table remains unavailable for direct browser reads or writes.
- Incident evidence uses a private bucket, owner-bound upload intents that expire after 20 minutes, and a registration RPC that checks the incident authorization and Storage object metadata. Reads are limited to the incident Captain and currently assigned Tanod; resident reporters and unassigned Tanods cannot read evidence. Files are restricted to PDF/JPEG/PNG and 10 MB. MIME metadata validation is not malware scanning or content inspection.
- Incident escalation is a Captain-only audit action for active incidents. It records the named recipient and handoff note only after explicit confirmation that an external handoff occurred; it never calls emergency services or represents an unverified contact as complete.
- Announcement audiences are enforced in Postgres. The officials-only audience uses a dedicated permission granted to barangay officials; resident memberships receive the general announcement permission only.
- Resident-only announcements are limited to active resident memberships. Role-targeted announcements require an active membership with the selected barangay role; publishers cannot select platform-scoped roles.
- In-app community notifications store only the recipient, source item reference, and read timestamp. Row policies re-check that the recipient still has access to the published source before showing or marking its notification read; no announcement body or advisory instructions are copied into the notification table.
- Notification preferences are scoped to the signed-in user's active barangay memberships. They control future in-app notification creation only and do not change authorization to read the underlying announcement or advisory.
- Health outreach stores event schedules only. BHWs can propose schedules, Captains review and publish them, and active barangay members can read published schedules. The workflow has no patient records, participant registration, diagnosis, or clinical advice. Event descriptions are still user-entered text and should contain no personal health data.
- SK event scheduling stores public event logistics only. SK Chairpersons can submit schedules for Captain review; active barangay members can read published events. It has no youth registry, participant registration, or attendance tracking, and descriptions should not contain private details about minors.
- SK accomplishment summaries are separate from internal project proposals and progress records. Only a completed project can be submitted; a different Captain must explicitly publish the curated title and summary. Active barangay members can read published summaries, while the underlying project, budget proposal, and internal updates remain restricted. The publication workflow cannot determine whether free text contains personal data, so the submitting official must review and minimize it.
- The accomplishment table has no direct authenticated SELECT grant. Its list RPC returns published summaries to active members while masking submitter and review-note fields; SK managers and Captain reviewers can read private review states.
- SK project audit history is returned through a tenant-checked RPC to SK managers and Captain reviewers. It shows the recorded action, staff display name, time, and action details; it does not grant direct client access to other event records.
- Residents may submit correction requests only for the profile linked to their authenticated account. `resident.update` staff review them through a security-definer RPC; the requester cannot approve their own changes, rejection requires a reason, only first name, last name and phone are changeable, and each submission/decision is logged. Client access to the event table and request actor IDs is withheld; requests are read through tenant/owner row policies.
- Resident data export resolves the signed-in account's linked resident record in the selected barangay, then fetches only that resident's verification and document-request rows under existing RLS policies. The JSON omits internal review notes and other residents' data. The downloaded file contains personal information, so the UI reminds residents to keep it private; the browser does not retain a server-side export copy.
- Correction decision notifications contain only a pointer to the request, are created by the authorized review RPC, and are visible only to the request owner with an active membership. The shared updates dialog displays a generic decision notice; the resident must open their resident workspace to see the status and any decline reason. These service notices remain enabled regardless of optional community-announcement preferences.
- Document types and applicant checklists are configurable by Captains and Secretaries through tenant-scoped RPCs. Applicants can read only types currently available for online requests. Checklist requirements are instructions only; the request flow does not accept supporting file uploads. Type changes record before/after values in a protected event table.
- Public document verification requires both the request reference and issuance number, each with random components. The RPC returns no holder name, address, purpose, or request ID; it reports only document type, issuing barangay, dates, and whether the issuance is valid, expired, revoked, or corrected. Apply the migration before directing the public to this page.
- A resident may withdraw only their own pending profile correction through a permission-checked RPC. Cancellation is audit logged, direct table writes remain unavailable, and the pending-only check prevents cancellation after staff review has begun.
- Document type configuration history is available only to users with `document.type.manage`, through a barangay-scoped RPC. It returns display names and recorded configuration values but withholds actor account IDs and direct access to the event table.
- Document request status notifications contain only a request reference and are refreshed on later status changes. Only the linked resident can read or mark them read, while active membership is required; they do not copy the request purpose or rejection reason into the inbox.

The included pgTAP tests have not been run in this workspace because no Supabase CLI, Docker, or configured database is available. This work is not a security certification. Apply and test the migrations in a disposable Supabase/Postgres environment before using real records.

Use separate development and production projects. Do not expose a service-role secret in the browser. Define formal retention, disclosure, incident response, backup, and privacy review procedures before production use.
